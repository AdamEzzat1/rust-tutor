# CLAUDE.md: rust-tutor

A symbolic (rule-based, deterministic, **no LLM in the feedback loop**) tutor
for scientific computing in Rust: the Rust counterpart of julia-tutor, held to
the same contracts. Design decisions and their reasons are in
`docs/DESIGN.md`; read it before changing scope.

## Commands

```bash
cargo build --release                      # the tutor; rust-toolchain.toml pins 1.97.1
T=target/release/tutor
$T check <paths...> [--hints=N]            # static checker; exit 1 on WARN, ADVICE never
$T rules                                   # every rule with FP risk and hints
$T scaffold odeint [--check]               # (re)generate / diff starter stages
$T start odeint 1 work/s1                  # copy a stage to work on (work/ is gitignored)
$T test work/s1                            # per-test results (compile errors are results too)
$T explain work/s1 --hints=1               # tests + compile errors + findings + measurements + where to start;
                                           # records hole attempts in .tutor/state.toml (--no-record)
$T progress                                # learner model: BKT per KC, hole attempts, reviews due
$T holemap odeint [--check]                # measured test->hole map + mutation tests (~3 min)
$T baseline odeint [--check]               # measurements of the reference
$T fixtures odeint [--check]               # explain on buggy fixtures vs golden outputs
$T lessons verify                          # run every lesson snippet on the pinned rustc
$T lesson L01                              # interactive lesson (state in .tutor/state.toml)
$T courses                                 # course manifests: units, outcomes
$T course list|record|verify [unit]        # record outputs; verify = re-run + grader self-tests
$T practice list | <id> [file.rs]          # show a problem / grade a solution
$T run file.rs                             # compile and run one file as the grader does
cargo test                                 # tutor tests (36)
(cd projects/odeint/reference && cargo test)   # the project's own tests (36 behaviour + allocation tests)
scripts/verify_all.sh                      # definition-of-done check: everything above (.ps1 on Windows)
```

## Layout

```
RUST_VERSION, rust-toolchain.toml  pinned release (1.97.1); every tool refuses any other rustc
crates/tutor/src/checker.rs        checker core: findings, severities, exit code, report
crates/tutor/src/rules.rs          RT001-RT007 on syn trees (one RuleMeta + visitor each)
crates/tutor/src/scaffold.rs       holes cut from the reference by `// HOLE: id` markers
crates/tutor/src/runner.rs         cargo test runs, libtest + rustc diagnostic parsing
crates/tutor/src/holemap.rs        measured test->hole map + mutation testing
crates/tutor/src/explain.rs        the explain step (deterministic text; error-code notes)
crates/tutor/src/models.rs         BKT, SM-2, Ochiai (pure functions)
crates/tutor/src/progress.rs       learner model over time (.tutor/state.toml)
crates/tutor/src/fixtures.rs       explain fixtures and golden outputs
crates/tutor/src/snippet.rs        compile-and-run one program (debug or release profile), cached by key
crates/tutor/src/lessons.rs        predict-the-outcome lessons; lessons/*.toml
crates/tutor/src/practice.rs       grading harness: cases, random cases, allocation count, timed ratio
crates/tutor/src/course.rs         units, course manifests, record, verify
projects/odeint/reference/         the project crate (no dependencies), tests/behaviour.rs, tests/alloc.rs,
                                   examples/measure.rs
projects/odeint/holes.toml         holes: stage, kc, summary, trivial bodies (mutants), measures
projects/odeint/{holemap,measure_baseline,fixtures}.toml, fixtures/, starter/   generated; never hand-edit
course/courses/*.toml              manifests (each unit in exactly one course); course/units/*.toml
course/outputs/*.toml              recorded example outputs (generated by `course record`)
```

## Stack-role group

The lead owns decisions. **Every reviewer gets a chance to object before a
milestone is called done.** Objections and their resolutions go in the
milestone's report (template at the end).

| Role | Owns | Must object when... |
|---|---|---|
| Lead: ITS architect | Scope, milestone order, trade-offs | Work drifts outside the current milestone |
| Rust language engineer | Reference code: ownership that teaches (split borrows, `&mut` workspaces), `Result` over panics for bad data, no `unsafe` without a stated invariant, clippy-clean | A hole lands in boilerplate instead of the concept; the reference uses a pattern the course tells learners to avoid |
| Numerical analyst | Algorithms, tolerances, convergence-order tests, floating-point honesty | A tolerance is picked to make a test pass rather than derived; a test compares floats with `==`; a solver isn't checked for its order |
| PL / static-analysis engineer | Checker rules on `syn` trees, the scaffolder, diagnostic parsing | A rule matches text instead of tree shape; a rule claims type knowledge only rustc has; a rule has no negative test |
| Performance engineer | Allocation counting, timed ratios, release vs debug | A performance claim is inferred where it could be measured; a timed verdict is put in a test |
| Test engineer | Tests as the specification, mutation testing, fixed RNG | A test checks code shape instead of behaviour; a hole passes with a trivial body; a test can flake |
| Sandbox / security engineer | Running untrusted code safely | Any path runs code from someone other than the local user before M4 lands |
| Toolchain engineer | Pinned rustc, lockfiles, CI, upgrade procedure | Anything depends on "latest stable"; a toolchain bump lands without re-verifying every key |
| Learning scientist (reviewer) | Hints, fading, knowledge components, misconception-tied distractors | A level-1 hint gives the answer; we measure completion instead of learning |
| Skeptic (reviewer) | Honesty | A claim ("fast", "zero-cost", "catches X") lacks a mechanism or a measurement |
| Plain-language editor | Whether a newcomer can follow | A term is used before it is defined; an analogy has no stated limit |
| Citation reviewer | Every reference is real and supports the sentence citing it | A reference has not been fetched and checked (see Known gaps: none are yet) |

## Invariants (never break; each has a test or a check)

1. **Style tolerance.** Every rule has a test showing two different correct
   styles produce zero findings (`crates/tutor/tests/checker_cases.rs`).
2. **ADVICE never changes the exit code** (`checker::exit_code`, tested).
3. **Determinism.** Same input, byte-identical checker and explain output;
   findings sorted; libtest thread ids stripped; tests run with
   `--test-threads=1`; every random test uses the in-tree SplitMix64 (stable
   by construction, unlike any crate's default RNG); hashes are FNV-1a with
   test vectors; never print HashMap iteration order unsorted.
4. **One pinned rustc.** `RUST_VERSION` and `rust-toolchain.toml` agree; every
   tool refuses another version (`util::require_pinned_toolchain`). Upgrading
   is its own milestone: re-run lessons verify, course record + verify,
   holemap, fixtures (rustc's error codes and messages, and float formatting,
   are what the keys depend on). `verified_on` in lessons must equal it.
5. **No answer leakage.** An opened hole contains only `todo!("TODO(hole:id)")`
   under its doc comment and signature (`tests/units.rs`, hole-leak test).
6. **The starter is generated, never hand-edited** (`scaffold --check`).
7. **Measured over inferred.** Allocation counts come from a counting global
   allocator; compile errors from rustc; convergence orders from fits; step
   counts from `Stats`. A static rule may only *point to* a likely location,
   and says so in its `fp_risk`.
8. **Numerical honesty.** Every numerical test and every practice tolerance
   states its derivation (error bound, order, conditioning) next to it. No
   float `==` in tests (RT001 is WARN). Every claim in unit prose that names a
   number was measured by `course record`; a claim the recorder cannot check
   (a notice) was compared by hand with the recorded output.
9. **Timings are never in tests.** Timed verdicts (`fast`, `slow`) are ratios
   to the reference in one process, re-measured on a borderline result, and
   labelled machine-dependent wherever they appear.

Also: every hole has trivial bodies in `holes.toml` that must fail a test
(`holemap --check`); every wrong lesson or question option maps to a
misconception; the reference has zero WARN findings from our own checker; the
odeint crate has no dependencies, and the tutor depends only on syn,
proc-macro2, quote, toml and serde (justified in DESIGN.md).

## Adding things

* **A rule:** a `RuleMeta` (id, kc, severity, honest `fp_risk`,
  `measured_by`, three hints, `answer_tokens` the level-1 hint must not
  contain) and a visitor in `rules.rs`; positive, negative and two-style cases
  in `checker_cases.rs`. Match on `syn` node shapes, never on text.
* **A hole:** `// HOLE: id` on the line directly above the function's first
  attribute or doc line; an entry in `holes.toml` with stage, kc and at least
  one trivial body; then `scaffold`, `holemap`, `baseline`, `fixtures` and
  commit the generated files.
* **A lesson:** `lessons/Lnn-name.toml`; every wrong option gets a
  misconception; `lessons verify`; set `verified_on`.
* **A unit:** see `course/AUTHORING.md`.

## Milestones and definitions of done

* **M1 (done): project slice.** odeint reference + tests, 7 holes over 2
  stages, scaffold, holemap (every mutant caught), baseline, checker with 7
  rules, explain with sole-cause + Ochiai ranking. DoD: `verify_all` passes.
* **M2 (done): feedback loop.** 8 explain fixtures with golden outputs
  (including a compile-error fixture, E0499), learner model (BKT + SM-2),
  4 lessons with verified keys.
* **C1 (in progress): courses.** 5 of 18 units ready. DoD per unit:
  `course verify` passes; every variant has the verdict it declares; every
  notice checked against the recorded output; references verified.
* **M3: second project** for the scicomp course (candidate: a CSR + CG solver
  with an iteration-count bound), so stage-2 material is not all ODEs.
* **M4: sandbox.** Run every learner submission in a container (no network,
  read-only root, unprivileged, resource limits), as julia-tutor does, before
  any server or website accepts code.
* **M5: website** from verified data only (lessons, explain goldens, hole map,
  rules), as in julia-tutor.

## Known gaps (be honest about them in reports)

* **No sandbox.** Everything runs as plain processes (README says so).
* **References not verified.** The units cite real works, but no reference
  has been fetched and checked against the sentence citing it.
  The citation reviewer's check is outstanding for every unit.
* **Timed verdicts are machine-dependent.** `layout-column-sums` declares
  the strided starter `slow` from three runs on one machine (8.05x, 9.32x,
  8.80x). `fast` claims rest on single verify runs. CI runners may differ.
  If one flips, drop the claim. Do not widen the threshold.
* **BKT parameters are priors, not fitted:** no learner data exists.
* **No growth or scaling verdict** (O(n) vs O(n^2)); only ratios at one n.
* **No learner has used it.** Nothing here is evidence about learning.
* **rustc diagnostics and `{:?}` float formatting are pinned, not stable:**
  a toolchain upgrade will change some keys (invariant 4 handles it).
* **The checker sees syntax only.** Rules cannot know types: RT001 misses
  `assert_eq!(a, b)` on two float variables (nothing in the syntax says they
  are floats; clippy's pedantic `float_cmp` has the types). Each rule's
  `fp_risk` states its own false positives and negatives.
